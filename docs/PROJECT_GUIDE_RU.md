# Подробный разбор проекта

Этот документ — путеводитель по проекту для разработчика с опытом нативного XCUITest. Английский `README.md` предназначен для проверяющего; здесь подробно объясняется устройство кода, запуск и диагностика.

## 1. Что именно автоматизируем

Приложение — Sauce Labs sample-app-mobile, релиз **2.7.1**. Проверяются три пользовательских сценария:

1. Сортировка всего каталога по цене от меньшей к большей.
2. Рисование на canvas и восстановление исходного состояния после Clear.
3. Переход в About, поворот в landscape и проверка работоспособности интерфейса.

Особенность релиза: About **открывает внешний Safari с сайтом saucelabs.com**, а не отдельный нативный экран приложения. Это подтверждено `DrawerLinks.js` upstream. Тест честно проверяет этот маршрут. Drawing содержит WebView с canvas и фоновой картинкой. «Чистый canvas» означает отсутствие добавленных штрихов, а не полностью белое изображение.

Локальный симулятор нужен для разработки. Требование задания — прогон всего набора на трёх реальных устройствах BrowserStack — проверяется отдельно. Локальные результаты нельзя выдавать за облачные.

## 2. Как взаимодействуют инструменты

```text
npm-команда
  → WebdriverIO runner читает конфигурацию
    → Mocha запускает describe / it / hooks
      → test вызывает методы Screen Objects
        → WebdriverIO отправляет WebDriver-команды
          → Appium выбирает XCUITest driver
            → WebDriverAgent выполняет XCTest-команды на iPhone
```

- **TypeScript** проверяет типы и помогает поддерживать контракты между слоями. Сам по себе он не проверяет, что локатор существует на устройстве.
- **Mocha** задаёт структуру тестов и управляет их жизненным циклом. Assertions здесь выполняются через стандартный `node:assert/strict`.
- **WebdriverIO** — клиент Appium и runner. Предоставляет `$`, `$$`, `browser`, ожидания, взаимодействие с элементами и репортёр.
- **Appium** — сервер автоматизации. Локально запускается отдельным процессом; в BrowserStack уже предоставляется сервисом.
- **XCUITest driver** связывает протокол Appium с iOS.
- **WebDriverAgent (WDA)** — XCTest runner, который строится Xcode для симулятора и принимает команды на устройстве.
- **pngjs** декодирует PNG для численной проверки canvas. Здесь нет AI-оценки изображения.

Аналогии с нативным опытом:

| Нативный XCUITest           | Здесь                                           |
| --------------------------- | ----------------------------------------------- |
| `XCUIApplication`           | Appium-сессия и `browser`                       |
| `accessibilityIdentifier`   | локатор `~test-...`                             |
| `XCUIElement`               | объект элемента WebdriverIO                     |
| `waitForExistence`          | `waitForExist`, `waitForDisplayed`, `waitUntil` |
| XCTestCase/test method      | Mocha `describe` / `it`                         |
| Page/Screen Object на Swift | класс в `tests/screens/`                        |
| XCTest attachment           | файлы в `artifacts/<session-id>/`               |

`waitForDisplayed` и существование элемента не равнозначны: iOS может включать в accessibility-дерево элементы за пределами экрана.

## 4. Почему Screen Object

Тест описывает намерение:

```ts
await new LoginScreen().signInAsStandardUser();
const drawing = await new SideMenu().openDrawing();
await drawing.drawZigzag();
await drawing.clear();
```

Тесту не нужно знать accessibility ID, координаты canvas и способ нажатия на пункт меню. Эти детали находятся в Screen Object или компоненте. Если меняется локатор, исправляется один класс, а не каждый test case.

Основные правила:

- Screen Object выполняет действия и возвращает данные.
- Проверки требований находятся в `spec`.
- Методы ожидания могут выбрасывать ошибки, если экран не открылся; это технический контракт метода.
- Общие меню выносятся в `components`, а чистые вычисления — в `support`.
- Элементы получаются через getters при обращении. Мы не сохраняем XCUIElement ID надолго, потому что после сортировки или поворота иерархия меняется.
- Базовый `BaseScreen` пока не нужен: полезного общего поведения мало. Создавать наследование ради одного `$` нет смысла.
- `async`/`await` обязателен: без `await` проверка может начаться раньше завершения действия.

## 5. Сортировка: что проверяет первый тест

1. Входит как `standard_user` через UI.
2. Проходит каталог до footer.
3. Считывает названия и цены видимых карточек.
4. Раскладывает карточки в визуальном порядке: сверху вниз, слева направо.
5. Убирает повторно увиденные карточки при перекрывающихся свайпах по имени товара.
6. Проверяет, что собраны все шесть товаров релиза 2.7.1.
7. Возвращается вверх и выбирает `Price (low to high)`.
8. Снова собирает каталог.
9. Проверяет совпадение набора названий и цен до/после.
10. Проверяет неубывание цен, включая допустимые равные цены.

`$7.99` превращается в `799`, а не сравнивается как строка. Неверный формат цены вызывает ошибку, а не превращается в `NaN` и не исчезает из проверки.

Число 6 — контроль полноты конкретного релиза. Если приложение изменится, его нужно пересмотреть. Дедупликация по имени предполагает уникальные названия товаров.

Возврат вверх использует ограниченные свайпы: `mobile: scroll` к первой карточке зависал на нашем симуляторе. Лимит не позволяет бесконечно прокручивать экран или молча возвращать неполный каталог.

## 6. Drawing: как доказать, что Clear работает

Проверка состоит из двух независимых условий:

- рисунок действительно изменил canvas;
- после Clear область вернулась к исходному изображению.

Если проверять только второй пункт, тест может ложно пройти, когда жест вообще ничего не нарисовал.

Сравнивается обрезанная область WebView внутри Drawing. Координаты переводятся из логических points в пиксели screenshot; 75 points снизу исключаются согласно CSS signature-pad релиза 2.7.1. WDA может вернуть полный экран даже для screenshot элемента, поэтому обрезка выполняется явно. В область входит фон canvas, но не status bar и нативные кнопки Clear/Save. Эталон создаётся **в этой же сессии на этом же устройстве**, поэтому нам не нужен отдельный baseline для каждого iPhone.

Перед снимком ожидается стабилизация изображения. Жест — зигзаг внутри области, координаты рассчитываются как доли её ширины и высоты. Системные края экрана не используются.

Сравнение:

- PNG декодируются в RGBA.
- Размеры снимков обязаны совпадать; несовпадение — ошибка.
- Пиксель считается изменённым, если хотя бы один канал отличается более чем на 24 из 255.
- После рисования должно измениться больше 0,1% пикселей.
- После Clear должно остаться **0 изменённых пикселей** с учётом указанного допуска по каналам.
- Крупный допуск по площади для оставшихся штрихов не используется.

Это визуальная проверка восстановления исходной области. Она не анализирует внутренний bitmap canvas через JavaScript и не подменяет Clear вызовом очистки DOM.

Unit-тесты отдельно доказывают, что неизменный фон проходит, нарисованный штрих обнаруживается, даже один оставшийся контрастный пиксель не проходит, мелкий шум допускается, а размеры не игнорируются.

## 7. Rotation: что считать «UI не сломан»

Сначала тест открывает About именно через меню приложения. Затем проверяет, что активен Safari и адрес содержит `saucelabs.com`, WebView загрузился и в нём есть видимые ссылки. Это отсеивает пустой браузер и типовую страницу ошибки соединения.

После поворота:

- `getOrientation()` возвращает `LANDSCAPE`;
- ширина окна больше высоты;
- ширина web-контента увеличилась относительно portrait;
- адресная строка и Reload остаются внутри viewport и доступны;
- нажатие Reload приводит к доступной загруженной странице;
- ориентация после действия остаётся landscape.

В `afterEach` восстанавливаются portrait и исходное приложение. Этот cleanup выполняется и при падении assertions. Снимок падения собирается общим hook.

Это **проверка работоспособности после поворота**, а не гарантия идеальной вёрстки каждого пикселя страницы. Сайт внешний и меняется независимо от APK/IPA. Сеть, Safari, cookie-баннер и изменения accessibility сайта — реальные внешние зависимости. На iOS 26.5 также наблюдалась ошибка XCTest `Unable To Rotate Device`; похожий сбой описан в [upstream issue #2829](https://github.com/appium/appium-xcuitest-driver/issues/2829). Перезапуск выделенного симулятора без стирания данных — допустимая диагностика окружения. Не следует скрывать такие ошибки через `skip` или подменять About локальной страницей.

## 8. Изоляция и жизненный цикл

Сейчас каждый spec содержит ровно один `it`. WebdriverIO создаёт отдельную сессию на spec; сценарии не должны зависеть от порядка. `maxInstances: 1` запрещает одновременную работу нескольких workers с одним локальным UDID и экономит trial concurrency.

`noReset: false` запрашивает стандартный сброс состояния приложения, но это не универсальная гарантия очистки всех iOS-хранилищ. Если логин сохраняется в конкретном окружении, следует переустановить только sample app или добавить явный logout в подготовку теста.

`fullReset: false` указан намеренно: в XCUITest полный сброс может стереть содержимое всего симулятора. Используем отдельный тестовый симулятор.

При добавлении второго `it` в один spec новой Appium-сессии автоматически не появится. Тогда нужно явно определить `beforeEach` для восстановления состояния.

Повтор тестов отключён: случайное падение должно быть видно. Retry сетевого запроса создания сессии — другая настройка, не повтор assertions; локально он тоже выключен.

## 9. Запуск на симуляторе

1. Установить Node и Xcode с iOS runtime.
2. В корне проекта выполнить `npm ci`.
3. Скачать simulator ZIP релиза 2.7.1 и распаковать в `apps/simulator` (команды в README).
4. Создать отдельный симулятор в Xcode или через `simctl`.
5. Получить UDID командой `xcrun simctl list devices available`.
6. Создать `.env` из `.env.example` и заполнить только локальные переменные:

```dotenv
IOS_SIMULATOR_UDID=идентификатор_твоего_симулятора
IOS_SIMULATOR_APP=apps/simulator/iOS.Simulator.SauceLabs.Mobile.Sample.app.2.7.1.app
```

В первом терминале:

```sh
npm run appium:local
```

Во втором:

```sh
npm run test:simulator
```

Только один сценарий:

```sh
npm run test:simulator -- --spec tests/specs/drawing-clear.spec.ts
npm run test:simulator -- --spec tests/specs/screen-rotation.spec.ts
npm run test:simulator -- --spec tests/specs/product-sorting.spec.ts
```

Первый запуск дольше: Xcode собирает WDA. Для создания локальной сессии выделено до десяти минут, включая до пяти минут на первую загрузку нового симулятора. `appium:processArguments` задаёт английский язык приложению без перезапуска системных служб Simulator.

UDID в README относится только к машине, на которой проект разрабатывался. На другой машине он не существует.

## 10. Запуск на BrowserStack

В `.env` задаются:

```dotenv
BROWSERSTACK_USERNAME=automation_username
BROWSERSTACK_ACCESS_KEY=access_key
BROWSERSTACK_APP_ID=bs://uploaded_app_id
IOS_DEVICE_NAME=точное имя устройства
IOS_PLATFORM_VERSION=точная версия iOS
BROWSERSTACK_BUILD_NAME=finonex-ios-suite
```

Нужен IPA **для реального устройства**, а не simulator `.app`. Пароль BrowserStack не используется в capabilities; Access Key берётся из аккаунта. Demo account приложения и аккаунт BrowserStack — разные сущности.

```sh
npm test
npm run test:sorting
npm run test:drawing
npm run test:rotation
```

Локальный Appium запускать не требуется. В облаке сервер и WDA предоставляет BrowserStack. Если `.env` неполный, конфигурация завершится с понятной ошибкой до создания сессии.

Чтобы покрыть три устройства текущей конфигурацией, нужно выполнить **все три сценария** трижды, меняя модель и версию ОС на доступные пары. Получится 9 успешных выполнений. Это последовательная матрица, а не уже встроенный параллельный запуск на трёх устройствах. Результаты и видео нужно сохранить по каждому устройству.

## 11. Где искать результаты

- В терминале: scenario, passed/failed, stack trace и время выполнения.
- `artifacts/logs/`: логи runner. Последующий запуск может перезаписать общий файл.
- `artifacts/<session-id>/<timestamp>-<test-name>/screen.png`: скриншот падения.
- В той же папке `source.xml`: accessibility-дерево на момент ошибки.
- `artifacts/<session-id>/canvas-before.png`: исходное состояние Drawing.
- `canvas-drawn.png`, `canvas-drawn-diff.png`: нарисованное состояние и подсветка изменившихся пикселей.
- `canvas-cleared.png`, `canvas-cleared-diff.png`: состояние после Clear и оставшиеся отличия.
- `canvas-comparison.json`: численные результаты сравнения.
- `about-portrait.png`, `about-landscape.png`, `about-layout.json`: доказательства поворота и геометрия.
- BrowserStack Dashboard: итог сессии, устройство, команды, видео. Статус выставляется по результату всей сессии, включая ошибки hooks.

Артефакты собираются до той стадии, до которой дошёл тест. Если Drawing не открылся, не будет снимка `canvas-drawn.png`, но общий failure screenshot и XML должны быть собраны. Ошибка сохранения диагностических файлов не должна скрывать первоначальное падение.

Файлы `.env`, apps и artifacts исключены из Git. Артефакты могут содержать данные экрана; в публичный репозиторий их нужно добавлять осознанно.

## 12. Как разбирать падение

| Симптом                       | Что проверять                                                             |
| ----------------------------- | ------------------------------------------------------------------------- |
| Missing BROWSERSTACK_*        | Выбран облачный config, но `.env` не заполнен                             |
| Simulator app not found       | Путь к `.app`, распаковку ZIP, рабочую директорию                         |
| Session creation timeout      | Appium запущен, runtime загрузился, Xcode собрал WDA                      |
| ECONNREFUSED 4723             | Нет локального Appium или занят/изменён порт                              |
| ECONNREFUSED 8100             | Не поднялся WDA; смотреть Appium/Xcode logs                               |
| Элемент не найден             | XML: правильный экран, английский язык, актуальный ID                     |
| Меню не открывается           | iOS touchable-wrapper; компонент использует native tap внутри элемента    |
| Drawing не загрузился         | WebView ещё загружается; не ослаблять assertion до «белая область есть»   |
| Рисование не изменило canvas  | Координаты, готовность WebView, screenshot/diff; такой тест обязан упасть |
| Clear оставил пиксели         | `canvas-cleared-diff.png`: реальный штрих или нестабильный фон            |
| About не загрузился           | Доступность сайта, сеть устройства, Safari, страница ошибки               |
| Rotation геометрия не совпала | Screenshot и `about-layout.json`, активное приложение, реальные bounds    |

После аварийной остановки Appium иногда остаётся временный lock запуска Simulator. Нельзя удалять такие lock-файлы без проверки, что владеющий процесс завершён: можно помешать другому тестовому запуску.

## 13. Как изменять и расширять проект

- Новый экран: класс в `screens`, приватные getters, действия и `waitForLoaded`.
- Повторяющийся элемент: `components`.
- Новый сценарий: отдельный `*.spec.ts`, ясные начальные условия и проверки результата.
- Изменился UI: сначала исследовать XML, затем исправлять Screen Object.
- Новая чистая логика проверки: `support` и небольшие unit-тесты на ошибки/граничные случаи.
- Новое устройство: настройка окружения, без копирования тестов.

Перед сдачей:

```sh
npm run check
```

Команда выполняет строгую проверку типов, проверку форматирования и unit-тесты. Она **не запускает E2E** и не расходует минуты BrowserStack. Для форматирования используется `npm run format`. Успешный typecheck не подтверждает работоспособность локаторов на реальном устройстве.

Не вводим автоматические retries, большие `sleep` и чрезмерные допуски сравнения ради зелёного отчёта. Сначала выясняем причину падения. Текущие известные ограничения и фактические результаты прогонов перечислены в README.

Локально каждый сценарий также успешно выполнялся на трёх сочетаниях модели и ОС. Особенности Safari и фактические версии ОС описаны в матрице устройств. Общий лимит Drawing составляет 300 секунд с учётом передачи скриншотов, критерий очистки холста остаётся прежним.

## 16. Быстрый запуск из приватного репозитория

`exercise.env` содержит тестовые API-ключи и идентификатор загруженного приложения по запросу владельца. Он загружается после `.env` без переопределения локальных значений. Для запуска всей матрицы достаточно `npm ci` и `npm run test:matrix`, пока аккаунт и приложение доступны. Пароль Google не используется. Эта конфигурация заменяет прежнее требование обязательно заполнять `.env` для облачного запуска.

## 17. Общая подготовка сессии

`tests/support/session-setup.ts` содержит `prepareSession()`. Общая конфигурация вызывает её через WebdriverIO `before` после создания Appium-сессии: portrait, вход стандартным пользователем и ожидание Products. При ошибке setup сохраняет screenshot/XML и пробрасывает исходную ошибку.

Каждый spec содержит один сценарий и получает новую сессию. Это подготовка один раз на сессию, а не `beforeEach`: если добавить несколько тестов в один файл, нужно отдельно обеспечить сброс состояния между ними. Переходы через меню в Drawing и About остаются в тестах. Rotation по-прежнему восстанавливает portrait в `afterEach`.

Этот рефакторинг проверен статически и unit-тестами. Ранее записанные успешные облачные сессии относятся к версии до переноса setup; новые E2E для этой правки не запускались.

## 18. Читаемые сценарии и отдельные проверки

`tests/specs/` содержит короткие сценарии: действия пользователя и именованные проверки. `tests/assertions/` содержит проверки каталога, холста и геометрии About. Screen Objects отвечают за локаторы, действия и ожидание экрана. `tests/support/device.ts` отвечает за поворот устройства и восстановление приложения.

Проверки сохраняют полный каталог из шести товаров и неизменность цен, порог появления рисунка 0,1%, отсутствие отличий после Clear с прежним цветовым допуском, изменение ориентации, границы элементов, загрузку страницы и Reload. Screenshot, diff и JSON остаются диагностическими артефактами. Комментарии в сценариях заменены понятными именами функций.

После выделения проверок выполнен `npm run check`; новые UI-прогоны не выполнялись. Ссылки BrowserStack показывают успешные сессии до рефакторинга.
